## Summary
Fetch job postings from **one** Apify actor (a Greenhouse board scraper), normalise them into `JobPosting`, and store them. This proves the sourcing path before Phase 2 adds more sources.

## User stories
- As the operator, I configure one Apify source so the MVP has real jobs to work with.
- As a candidate, I see the sourced jobs in a list.

## Scope
**In:**
- `IJobSource` interface and `ApifyJobSource` implementation
- Apify token and actor id read from configuration and secrets
- Normalisation to `JobPosting`
- Exact-hash duplicate check
- Apply-path classification (ATS URL / email / native / unknown)
- Manual "fetch now" trigger

**Out:**
- More than one source, shared scheduling, the budget meter (F2.1)
- Fuzzy duplicate detection (F2.2)

## Business rules
1. The Apify token is never stored in code or the database. It comes from user-secrets locally and from the secret store in production.
2. Each posting stores: source, external id, company, title, location, remote flag, description, apply URL, apply path, posted date, and a content hash.
3. A posting with the same content hash as an existing one is not inserted again.
4. Actors run without any user credentials or cookies.

## Acceptance criteria
1. Given a configured actor and token, when I trigger a fetch, then the new postings are stored and listed.
2. Given the same fetch run twice, then no duplicate postings are created.
3. Given a posting whose apply link is a Greenhouse URL, then its apply path is `AtsUrl`.
4. Given a missing or invalid token, when a fetch runs, then it fails with a logged error and the UI shows "Source unavailable"; existing postings are unaffected.

## Edge cases
- The actor returns malformed items -> those items are skipped and counted in the run log; the run still succeeds.
- The actor run times out -> it is marked failed; no partial duplicates are stored.

## NFRs
- One fetch completes within the actor's run time plus < 30 s of processing for 500 items.
