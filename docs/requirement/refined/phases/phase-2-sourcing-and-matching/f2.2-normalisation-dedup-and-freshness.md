## Summary
Turn raw actor items into canonical postings, remove exact and near duplicates across sources, and drop stale or closed roles.

## Scope
**In:**
- Canonical `JobPosting` mapping per source
- Company-name normalisation (`CompanyKey`)
- Title normalisation
- Content hash
- Near-duplicate rule
- Freshness and closed-posting handling

## Business rules
1. **Exact duplicate:** the same content hash (company + title + location + description shingle) -> not stored again.
2. **Near duplicate:** the same `CompanyKey` and normalised title within 30 days, on any source -> linked as one canonical posting. Its other sources are kept as alternate links.
3. When a canonical posting has several apply paths, they are preferred in this order: `AtsUrl` > `Email` > `NativeApply` > `Unknown`.
4. Postings older than 30 days, or reported closed by their source, are marked `Closed` and excluded from new cycles.

## Acceptance criteria
1. Given the same role from Greenhouse and from LinkedIn, then one canonical posting exists, with the Greenhouse ATS URL as its apply path.
2. Given a repost with an edited description within 30 days, then it is linked to the existing posting, not created as a new one.
3. Given a posting 31 days old, then it is `Closed` and no cycle picks it up.
4. Given "Acme Inc." and "ACME, Inc", then both normalise to the same `CompanyKey`.

## Edge cases
- E1: reposts and cross-source copies -> at most one application (enforced by the ledger in F3.8).
- The same title at the same company but for different locations -> kept separate (location is part of the hash).

## NFRs
- Duplicate checks add < 50 ms per posting.
