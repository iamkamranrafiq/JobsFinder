## Summary
A per-user ledger guarantees one application per job, and a strict state machine guarantees that statuses are truthful. This feature enforces the 100% honesty invariant.

## Scope
**In:**
- `Application` state machine
- Unique ledger indexes
- `ApplicationEvent` log
- Idempotency keys
- Honesty invariant tests and alert hook (F1.5)

## Business rules
1. States:
   - `Prepared`
   - `Queued`
   - `Submitted`
   - `NeedsYou(reason)`
   - `Failed(reason)`
   - (internal, not shown in the tracker) `Skipped`, `Expired`, `Cancelled`

   Only the defined transitions are allowed. `Submitted` is reachable **only** from a channel confirmation.
2. Unique indexes:
   - `(TenantId, JobHash)`
   - `(TenantId, CompanyKey, NormalisedTitle)` within a 30-day window

   Together they prevent duplicate applications across sources and reposts (E1).
3. Retries are safe. A half-finished apply resumes or fails, and is never silently re-submitted (E19).
4. Each `Application` stores the profile version used.

## Acceptance criteria
1. Given an attempt to transition to `Submitted` without a confirmation record, then the domain refuses it (unit test).
2. Given the same job reached through two sources, then a second application is refused by the ledger.
3. Given the invariant check job runs, then it finds zero `Submitted` rows without confirmation evidence. Otherwise the operator is paged.
