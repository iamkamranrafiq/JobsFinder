## Summary
A durable, Postgres-backed job queue consumed by hosted workers. Cycles and apply jobs survive restarts and resume from the last completed stage.

## User stories
- As a user, I don't lose a cycle in progress when the server restarts.

## Scope
**In:**
- Job table (type, tenant, payload, state, attempts, next-run time, lock)
- Worker host
- Retries with exponential backoff
- Stage checkpointing for cycles
- Dead-letter state
- Per-tenant fairness

**Out:**
- External brokers (RabbitMQ / Service Bus); they are only needed at scale

## Business rules
1. Jobs are claimed with row locks (`SELECT ... FOR UPDATE SKIP LOCKED`), so each job is processed by one worker only.
2. Retry policy: 3 attempts with exponential backoff, then dead-letter with the error.
3. A cycle records each completed stage. After a crash, it resumes from the next stage.
4. An **apply** job that crashed after clicking submit is never retried automatically. It becomes `NeedsYou(Unconfirmed)` (E19).
5. Fairness: one tenant cannot occupy more than half of the worker slots while other tenants have queued work.

## Acceptance criteria
1. Given a cycle killed mid-stage, when the worker restarts, then the cycle resumes from that stage and completes.
2. Given a job failing 3 times, then it is dead-lettered and visible to the operator.
3. Given two workers, then no job runs twice concurrently (load test with 1,000 jobs).
4. Given an apply job interrupted after submit, then it ends as `NeedsYou(Unconfirmed)` and is not re-submitted.

## Edge cases
- Database unavailable -> workers back off and resume; no job is lost.

## NFRs
- Enqueue-to-start latency p95 < 5 s when idle.

## Dependencies
- F1.2 (tenant context per job)

## Open points
None.
